# PRD: Дашборд качества AI-ассистента (production)

Задача для архитектора | Владелец: AI Adoption | Дата: 20.08.2026 | Приоритет: high

## 1. Суть и цель

Построить production-версию дашборда качества AI налогового ассистента для МСБ: автоматический сбор логов диалогов, LLM-оценка качества ответов по фиксированной таксономии и веб-дашборд для продакт-команды. Прототип UI утверждён и задеплоен: https://ai-quality-dashboard-teal.vercel.app (single-file HTML, загрузка CSV, расчёт client-side). Прототип задаёт состав экрана и метрик; архитектор проектирует backend-пайплайн и замену ручной загрузки файла на автоматический поток данных.

## 2. Метрики (состав экрана зафиксирован прототипом)

| Блок | Содержимое | Источник |
|---|---|---|
| KPI-ряд | Диалогов за период; время ответа: среднее, медиана, p90; % правильных; % воды | Логи + разметка |
| Тренд | avg / median / p90 времени ответа по дням | Логи |
| Качество ответов | Правильный / частично верный / вода / ошибка (доли и счётчики) | LLM-judge |
| Дефекты ответов | Счётчики по таксономии дефектов (см. п. 4) | LLM-judge |
| Категории вопросов | Распределение диалогов по темам | LLM-классификатор |
| Топ вопросов | Частые формулировки после кластеризации, счётчик и доля | Кластеризация |

## 3. Функциональные требования

| ID | Требование | Примечание |
|---|---|---|
| FR-1 | Ingest логов диалогов ассистента: вопрос, ответ, timestamp, latency (мс), session_id | Источник: backend ассистента (FastAPI, OpenAI API) |
| FR-2 | Latency-метрики считаются по всем диалогам: avg, median, p90 за произвольный период | Перцентили по сырым значениям, не по дневным агрегатам |
| FR-3 | LLM-judge: автоматическая разметка каждого ответа вердиктом и дефектом по таксономии п. 4 | Промпт и таксономия версионируются; поле confidence |
| FR-4 | LLM-классификация вопроса по категориям + кластеризация формулировок для топа | Категории из справочника, расширяемого без деплоя |
| FR-5 | Дашборд: периоды сегодня / 7 / 30 / квартал / всё, автообновление не реже 1 раза в сутки | UI-эталон: прототип |
| FR-6 | Drill-down: клик по дефекту или категории открывает список диалогов с текстами вопрос-ответ | Нужно для разбора и пополнения базы знаний |
| FR-7 | Ручная корректировка вердикта разметчиком поверх LLM-оценки; история правок | Ручная метка приоритетнее LLM |
| FR-8 | Экспорт среза в XLSX / CSV | Формат колонок как в прототипе |
| FR-9 | Fallback: загрузка CSV / XLSX / JSON руками, как в прототипе | Пока ingest не подключён, дашборд уже полезен |

## 4. Таксономия разметки (утверждена, разметка 19.08.2026)

**Вердикты:** правильный, частично верный, вода / нет прямого ответа, ошибка.

**Дефекты:** вода / нет прямого ответа; ошибка в цифрах; устаревшая ставка (ИПН); пробел в базе знаний; противоречие в ответе; вне тематики; повтор без улучшения.

**Категории вопросов:** форма 910 и СНР; ИПН и зарплата; соцплатежи (ОПВ, ВОСМС, СО); сотрудники и кадры; НДС и пороги; прочее.

## 5. Ограничения и контекст

- Корпоративный файрвол: хостинг на внешнем VPS (Docker Compose), не во внутренней сети.
- Стек команды: Python + FastAPI, React, PostgreSQL; расписания: APScheduler. Не плодить новые технологии без причины.
- Оценка LLM-judge стоит денег: бюджет на разметку считать заранее (объём около 200-400 диалогов в день); допустимо семплирование, но latency-метрики всегда по 100% диалогов.
- ПДн: в логах возможны ИИН и суммы; определить политику маскирования до передачи в LLM-judge.
- Доступ к дашборду: только команда (auth обязателен, достаточно простого).

## 6. Что ждём от архитектора

- Схема пайплайна: ingest, очередь разметки, хранение (модель данных), API дашборда, частота пересчёта.
- Решение: разметка онлайн (по каждому диалогу) или батчем по расписанию; обоснование по стоимости и задержке данных.
- Выбор judge-модели и стратегия контроля качества разметки (калибровка по ручной выборке 100 диалогов, есть от 19.08).
- Оценка объёма работ по фазам: MVP (FR-1, 2, 3, 5, 9) и полная версия (остальное).
